feat(admin-credit): Phase 1C-1 — record admin credits as OBSERVER_EVENT

The POST /api/v1/admin/credit endpoint now records every credit
action as a non-balance OBSERVER_EVENT transaction in the audit
trail. The actual balance change still uses addBalance (since
admin credit is a privileged override, not a protocol event).

CHANGES
- src/http/routes/bootstrapApi.js
  - POST /api/v1/admin/credit
    - Step 1: Apply an OBSERVER_EVENT tx (event: 'ADMIN_CREDIT')
              with full metadata (amount, reason, admin_action flag)
    - Step 2: Apply the actual balance credit via addBalance
    - Response now includes txHash + auditEvent
    - Error handling: returns 500 AUDIT_FAILED if event tx fails
  - Added import: buildObserverEvent from transactionBuilder

DESIGN RATIONALE
Why OBSERVER_EVENT (not a new tx_type)?
- The admin credit is a privileged, non-protocol action
- It must be auditable but does not represent a balance flow
  between accounts
- OBSERVER_EVENT is the right semantics: "something happened,
  record it, no balance effect"

Why keep addBalance for the actual credit?
- Admin credit is an override of state (not a transfer)
- It does not move tokens between accounts
- It does not need a from/to pair
- Future: could create ADMIN_CREDIT tx_type if full audit
  of balance change is needed

WHY THIS IS THE RIGHT PHASE 1C-1
- Lowest risk file: 1 call site
- Establishes the pattern: build tx → apply → get txHash → respond
- Validates end-to-end: tx → txHistory → queryable → persisted
- Sets up future phases (1C-2 through 1C-7) to follow same pattern

RESPONSE FORMAT
Before:
  { success, address, amount, before, after }
After:
  { success, address, amount, before, after, txHash, auditEvent }
